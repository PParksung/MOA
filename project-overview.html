MOA — 프로젝트 가이드

실제 시세로 연습하는 AI 모의투자 플랫폼 · "투자, 먼저 모아보세요."

프로젝트 소개

MOA(Mock Onboarding to Assets)는 실제 한국투자증권(KIS) 시세를 바탕으로 100만원 가상 자금을 가지고 주식 투자를 연습할 수 있는 모의투자 플랫폼이다. AI가 사용자의 거래 패턴을 분석해 피드백을 제공하는 것이 핵심 차별점이다.

문제 정의 & 해결책

문제 정의

주식 투자에 관심은 있지만 실제 돈을 잃을까봐 시작을 못 하는 사람들이 많다. 기존 증권사 모의투자 서비스에는 세 가지 진입 장벽이 있다.

  • 실제 계좌 개설 + 본인인증 필요 → 진입 장벽 높음
  • HTS/MTS UI가 전문 트레이더용 → 입문자에게 복잡함
  • 투자 후 피드백 없음 → 뭘 배웠는지 모름

해결책

  • 이메일만으로 즉시 가입, 100만원 가상 자금 자동 지급
  • 입문자 친화적 심플 UI
  • AI가 내 투자 패턴을 분석해 피드백 제공 핵심 차별점
왜 100만원인가? 실제 입문자가 처음 투자할 때 넣는 현실적인 금액이자, 다양한 종목을 경험하기에 충분한 금액. 자산 리셋은 1주일에 1회로 제한해 현실감 유지.

포트폴리오 목적

충남대 컴공 4학년, 은행 IT 공채(KB / 신한 / 하나 / 우리) 준비. 금융 도메인 이해 + 백엔드 시스템 설계 + AI 연동 역량을 보여주기 위한 프로젝트.

시스템 아키텍처

외부 단일 진입점은 Nginx. Spring Cloud Gateway가 경로 기반으로 4개 서비스에 라우팅하고, exchange-server는 내부 호출만 허용한다. 시세·체결 알림은 WebSocket 역방향 푸시로 전달된다(Nginx·Gateway가 WS 프록시 담당). 체결 이벤트는 Kafka로 발행되어 ai-server가 구독하고, Prometheus + Grafana가 전 서버 메트릭을 수집한다.

사용자 인증

  • 회원가입: 이메일 + 비밀번호 (BCrypt 해싱) SHA-512에서 변경
  • 가입 시 현금 계좌 자동 개설 + 100만원 자동 지급
  • 로그인 → JWT 발급 (access 5분 / refresh 1주일)
  • 토큰 재발급: Refresh Token Rotation — 재발급 시 refresh token도 새로 발급, 이전 토큰 재사용 감지 시 해당 유저 토큰 전체 무효화 (탈취 대응)
  • 자산 리셋: 잔액 부족 시 100만원으로 초기화 가능 (1주일에 1회 제한)
왜 SHA-512 → BCrypt인가? SHA-512는 빠르게 계산되도록 설계된 범용 해시라 GPU 브루트포스에 취약하다. 비밀번호 해싱은 일부러 느리게 동작하는 BCrypt(또는 Argon2)가 표준이며, Spring Security의 BCryptPasswordEncoder를 사용한다. salt 자동 포함 + work factor 조절 가능.
완전 무제한 리셋은 투자 의미가 없어지므로 제한을 둠. 1주일 동안은 현실처럼 신중하게 투자하도록 유도.

현금 / 증권 계좌

현금 계좌

  • 계좌번호 AES-256-GCM 암호화 저장 (777XXXXXXXX1 형식) CBC에서 변경
  • 잔액 조회: 예치금 / 매수 묶인 금액 / 출금 가능 금액
  • 입금 · 출금 · 거래 내역 조회 (페이징)
  • 계좌 정지 · 해제
왜 CBC → GCM인가? CBC는 암호화만 하고 무결성 검증이 없어 패딩 오라클 공격 등에 취약하다. GCM은 인증 태그가 포함된 AEAD 방식이라 복호화 시 데이터 변조까지 감지한다. 현재 권장 표준. 암호화 키는 application.yml 평문 저장 금지 → 환경변수로 주입 (장기적으로 Vault 고려).

증권 계좌

  • 종목별 계좌 개설
  • 잔고 조회: 보유량 / 매도 묶인 수량 / 매도 가능 수량
  • 계좌 정지 · 해제

실시간 시세 (KIS API)

  • 장중 (평일 09:00~15:30): KIS WebSocket 실시간 시세
  • 장외: 마지막 종가 유지
  • 종목 목록 + 현재가 + 등락률 제공
  • 시세 Redis 캐싱

주문 및 체결

  • 매수 / 매도 주문 접수
  • 호가 단위 검증 (가격 구간별)
  • 상하한가 검증 (±5%)
  • 다자간 상대매매 (동일 가격 FIFO 체결)
  • 미체결 주문 조회 / 체결 내역 조회 / 주문 취소

오더북 (Redis)

키 패턴타입설명
{stock_id}:{side} ZSET LIST에서 변경 가격 목록 (score = 가격). 최우선 호가를 O(log N)에 조회
{stock_id}:{side}:{price} LIST 주문 FIFO 큐
{stock_id}:{side}:total-unit HASH 가격별 잔량

왜 가격 목록을 LIST → ZSET으로 바꿨나?

체결 엔진은 항상 최우선 호가(매수 최고가 / 매도 최저가)를 찾아야 한다. LIST는 정렬을 보장하지 않아 매번 전체 스캔이 필요하지만, ZSET은 score를 가격으로 두면 ZRANGE / ZRANGE REV 한 번으로 최우선 호가를 꺼낼 수 있다. 가격별 주문 FIFO(LIST)와 잔량(HASH)은 그대로 유지.

오더북 정합성 설계

  • Lua 스크립트로 원자적 체결: 체결 1건은 Prices(ZSET) · Orders(LIST) · TotalUnits(HASH) 3개 키를 동시에 갱신한다. 중간에 실패하면 오더북이 깨지므로, Redis Lua 스크립트로 묶어 원자적으로 실행
  • DB가 source of truth: Redis 장애·재시작 시 오더북이 유실될 수 있으므로, MySQL의 미체결 주문(orders)으로 오더북을 언제든 재구성 가능하게 설계
  • 정합성 대사(Reconciliation) 배치: DB 주문 상태와 Redis 오더북을 주기적으로 비교·검증

AI 투자 패턴 분석 핵심 차별점

  • 거래 내역 기반 분석: 평균 보유기간 / 승률 / 손절 평균 / 주요 거래 시간대
  • LLM이 패턴 기반 피드백 리포트 자동 생성
  • FDS (이상거래 탐지) 은행권 핵심 키워드: 룰 기반 탐지(단시간 동일 종목 반복 주문, 자전거래 패턴 등) + LLM 분석 조합
  • LLM 호출부는 LlmClient 인터페이스로 추상화 — v1.0 이후 파인튜닝 모델 교체 실험에 대비해 구현체(GeminiClient)만 갈아끼울 수 있는 구조로 설계
FDS(Fraud Detection System)는 은행 IT의 핵심 시스템이다. 이상거래 탐지를 FDS로 브랜딩하면 "모의투자 + FDS 구현 경험"이라는 독특한 조합이 된다.

항목현재개선이유

금액·수량 타입 일부 INT BIGINT 통일 INT 최대 약 21억 — 잔액 × 수량 곱셈에서 오버플로 가능

보안 설계 은행 IT 핵심

면접에서 바로 검증당하는 영역. 각 선택의 "왜"를 설명할 수 있어야 한다.

영역설계이유
비밀번호 BCrypt (SHA-512에서 변경) SHA-512는 빠른 범용 해시 → GPU 브루트포스 취약. BCrypt는 의도적으로 느림 + salt 내장
계좌번호 암호화 AES-256-GCM (CBC에서 변경) CBC는 무결성 검증 없음(패딩 오라클 취약). GCM은 AEAD — 변조 감지 포함
암호화 키 관리 환경변수 주입 (장기: Vault) application.yml 평문 저장 금지. 키와 코드의 분리
Refresh Token Rotation + 재사용 감지 재발급 시 refresh도 교체. 이전 토큰 재사용 = 탈취 신호 → 전체 무효화
서버 간 인증 exchange-server 내부 API 키 Docker 네트워크 분리만으로는 부족. 내부 호출도 인증 계층 추가
Rate Limiting Gateway에 Bucket4j 무차별 요청 차단. FDS(이상거래 탐지)와 연결되는 스토리

트랜잭션 & 동시성 설계 최대 차별화 포인트

돈이 오가는 시스템에서 가장 중요한 영역이자, 은행 IT 면접에서 가장 깊게 파고드는 주제. 시나리오별로 설계를 명확히 한다.

1. 잔액 갱신 동시성 (Race Condition)

같은 유저가 동시에 매수 주문 2건을 넣으면 tied_savings 갱신이 꼬일 수 있다.

  • 비관적 락 (SELECT ... FOR UPDATE): 현금/증권 계좌 잔액 갱신에 적용. 돈 관련 로직은 충돌 시 실패하면 안 되므로 락을 먼저 잡는다
  • 낙관적 락 (JPA @Version): 충돌이 드문 영역(계좌 정지/해제 등)에 적용
  • "어디에 어떤 락을 왜 썼는지" 설명 가능해야 함 — 면접 단골 주제

2. 분산 트랜잭션 — Saga 패턴 (보상 트랜잭션)

주문 흐름: 돈 묶기(MySQL) → 체결(exchange Redis) → 결과 반영(MySQL). 서로 다른 저장소를 거치므로 하나의 DB 트랜잭션으로 묶을 수 없다.

  • 보상 트랜잭션: 체결 거절/실패 시 묶어둔 금액을 되돌리는 명시적 보상 단계 정의
  • 타임아웃 처리: exchange-server 응답 유실 시 "체결됐는지 모르는 상태" 발생 → 주문 상태를 UNKNOWN으로 두고 재조회로 확정
  • 멱등성 키: order_id 기반 멱등 처리 — 재시도해도 중복 체결 방지
  • 대사(Reconciliation) 배치: DB 주문 상태 ↔ Redis 오더북 주기적 비교·검증. 은행에서 실제로 쓰는 용어/프로세스

3. Redis 오더북 원자성

  • 체결 1건 = 3개 키(ZSET/LIST/HASH) 동시 갱신 → Lua 스크립트로 원자적 실행
  • Redis 유실 대비: DB가 source of truth, 미체결 주문으로 오더북 재구성 가능하게 설계

차별화 강화

FDS 브랜딩 은행권 키워드

이상거래 탐지를 FDS(Fraud Detection System)로 브랜딩. 룰 기반(단시간 반복 주문, 자전거래 패턴) + LLM 분석 조합으로 "모의투자 + FDS 구현 경험"이라는 독특한 조합을 만든다.

체결 실시간 알림 (WebSocket)

WebSocket으로 체결 알림 + 시세 푸시를 구현한다. 시세처럼 빈번한 데이터에 표준적인 선택이고, KIS 연동도 WebSocket이라 기술 일관성이 있다. Nginx와 Gateway가 WS 프록시를 담당한다.

Kafka 이벤트 아키텍처

체결 이벤트를 exchange-server가 Kafka로 발행하고 ai-server가 구독한다. 체결 흐름(동기)과 분석 흐름(비동기)을 분리해 MSA 간 결합도를 낮추고, ai-server 장애가 체결 성능에 영향을 주지 않는 구조를 만든다.

AI 파인튜닝 실험 계획 v1.0 출시 이후

투자 패턴 피드백 리포트를 생성하는 AI를 파인튜닝하고, 프롬프트 기반 Gemini와 같은 지표(품질·비용·지연시간)로 비교하는 실험. 파인튜닝 자체보다 "측정 → 개선 → 비교"의 과정이 면접·블로그에서 핵심 스토리가 된다. GPU 없이 진행 가능한 경로로 설계했고, 이 문서만 보고 따라할 수 있게 단계별로 정리.

전제 (v1.0 개발 중에 미리 해둘 것 — 2가지):
① ai-server의 LLM 호출부를 LlmClient 인터페이스로 추상화 (GeminiClient 구현체). 실험 때 OllamaClient / TunedGeminiClient를 추가해 설정만으로 교체.
② 리포트 생성 시 입력(패턴 요약 JSON)과 출력(리포트)을 DB나 파일로 로깅. 이 로그가 나중에 평가셋의 재료가 된다.

Phase 0 — 베이스라인 측정 약 반나절

  • 대표 거래 패턴 30개를 선정 (실사용 로그 + 직접 만든 엣지케이스: 무손절형, 단타 과다형, 한 종목 몰빵형 등)
  • 현재 프롬프트 방식(Gemini)으로 30개 전부 리포트 생성
  • 스프레드시트에 기록: 품질 루브릭 점수(아래 Phase 3 기준표) · 1건당 토큰 비용 · 응답시간 p50/p95
  • 이 수치가 모든 비교의 기준선. 이것 없이 파인튜닝부터 하면 "좋아졌는지"를 증명할 수 없다

Phase 1 — 학습 데이터셋 구축 1~2일

  • 입력 스키마 고정: 패턴 요약 JSON (평균 보유기간, 승률, 손절 평균, 주요 거래 시간대, 종목 편중도, 리셋 횟수 등 — ai-server 분석 결과와 동일 형식)
  • 가상 패턴 생성기 작성: 필드 조합을 코드로 랜덤 생성해 500~1,000개 패턴 생성. 균등 랜덤만 쓰지 말고 유형별(공격적/보수적/비합리적)로 비율을 정해 생성
  • 정답 리포트 생성 (지식 증류): 잘 다듬은 프롬프트 + Gemini(temperature 0.3 이하)로 각 패턴의 "정답 리포트"를 생성
  • 품질 검수: 전체의 10%를 직접 읽고 수치 오류·뻔한 소리·환각이 있는 쌍은 제거
  • 분리: train 90% / eval 10%. eval 셋은 학습에 절대 사용 금지
# 학습 데이터 JSONL 형식 (1줄 = 1예제)
{"messages": [
  {"role": "system", "content": "너는 투자 입문자를 위한 패턴 분석 코치다..."},

]}

Phase 2-A — 경로 ①: 관리형 파인튜닝 약 반나절

  • Vertex AI의 Gemini Flash supervised tuning 사용 (이미 Gemini를 쓰므로 서빙 코드 변경 최소)
  • 절차: GCP 프로젝트에서 Vertex AI 활성화 → JSONL을 Cloud Storage 버킷에 업로드 → 콘솔에서 튜닝 잡 생성(epoch 등 기본값으로 시작) → 완료 후 엔드포인트 발급
  • ai-server에서 모델명만 튜닝된 모델 ID로 교체 (TunedGeminiClient)
  • 비용: 수백~수천 예제 기준 수 달러 수준. 잡 생성 전 콘솔에서 예상 비용 확인

Phase 2-B — 경로 ②: 오픈모델 QLoRA + 로컬 서빙 2~3일

학습 경험을 직접 어필하고 싶을 때. GPU는 무료 클라우드, 서빙은 보유한 Apple Silicon Mac으로.

  • 학습 환경: Google Colab 무료 T4 (또는 Kaggle 주당 GPU 30시간). unsloth 라이브러리 사용 — T4 한 장으로 3B급 QLoRA 가능
  • 베이스 모델: 한국어 가능한 소형 모델 — Qwen2.5-3B-Instruct 또는 EXAONE-3.5-2.4B-Instruct
  • 학습 설정 시작점: QLoRA 4bit, LoRA r=16 / alpha=32, learning rate 2e-4, epoch 2~3. eval loss가 내려가다 다시 오르면 그 직전 체크포인트 사용 (과적합)
  • 변환·서빙: 학습 결과를 GGUF로 변환 → Q4_K_M 양자화 → Mac에서 Ollama Modelfile로 등록 → localhost:11434 API 확인
  • ai-server에 OllamaClient 구현체 추가, 설정으로 전환

Phase 3 — 평가 및 비교 약 1일

  • eval 셋(학습 미사용) 50개 패턴으로 3개 모델 동일 실행: ① 프롬프트 Gemini(베이스라인) ② 튜닝 Gemini ③ 로컬 QLoRA 모델
  • 품질 루브릭 (각 1~5점): ① 수치 인용 정확성(입력 JSON의 숫자를 틀리지 않게 인용) ② 구체성(뻔한 조언이 아닌 패턴 기반 지적) ③ 실행 가능성(다음 주에 해볼 행동 제시) ④ 형식 준수(섹션 구조·길이) ⑤ 환각 없음(입력에 없는 사실 창작 금지)
  • 채점 방법 2중화: LLM judge(생성에 안 쓴 다른 모델로 루브릭 채점) + 본인 블라인드 채점(어느 모델 출력인지 가린 상태로 샘플 15개)
  • 비용·지연 측정: 1리포트당 원가(로컬 모델은 0원 처리), 응답시간 p50/p95
  • 결과를 표로 정리 → 블로그 발행: "프롬프트 vs 파인튜닝, 투자 리포트 생성 3종 비교"

주의사항
· 합성 데이터 증류 시 사용하는 LLM 제공자의 약관 확인 (경쟁 모델 학습 용도 제한 조항이 있는 경우가 있음 — 학습용 포트폴리오 범위에서 확인 후 진행)
· 패턴 생성기는 시드 고정 — 실험 재현 가능하게
· 리포트에 투자 조언 면책 문구 포함 ("교육용 분석이며 투자 권유가 아님")
· FDS(이상거래 탐지)는 이 계획과 무관 — 수치 분류는 scikit-learn 등 고전 ML로 별도 구현 (GPU·파인튜닝 불필요)

스토리텔링 팁: "처음엔 SHA-512 / LIST로 설계했다가 왜 잘못인지 학습하고 BCrypt / ZSET으로 개선했다"는 과정 자체가 블로그 글감이자 면접 스토리가 된다. 변경 이유를 커밋·블로그에 남길 것.
